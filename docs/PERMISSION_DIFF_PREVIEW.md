# Permission Diff Preview Before Policy Changes (#1173)

## Overview

The Permission Diff Preview system (`lib/permission-diff.ts` and `backend/src/routes/permissionPreview.ts`) computes deterministic, before-and-after visual and structured diffs before any role-based access control (RBAC) policy changes are committed to the system.

By introducing pre-flight evaluation, maintainers can inspect changes to permissions, affected actions, impacted scopes, and affected actor identities before applying updates. High-risk operations (such as broad permission additions or removals across critical roles) require cryptographic content-bound confirmation tokens, preventing accidental privilege escalation or service outages.

---

## Architecture & Core Mechanics

### 1. Diff Computation (`computePermissionDiff`)
Takes the current policy configuration and proposed policy specification:
- Compares each role's permission set to identify `addedPermissions`, `removedPermissions`, and `unchangedPermissions`.
- Computes affected higher-level actions (e.g. `withdraw`, `emergency_pause`, `admin_manage`) and scopes (`finance`, `admin`, `system`).
- Aggregates actor impacts: any actors possessing modified roles are inventoried, detailing net permission differentials.
- Classifies operations into `isNoOp` (identical configuration) or `isBroadChange` (mass grant or revoke surpassing security thresholds).

### 2. High-Risk / Broad Change Guard (`preparePolicyChange`)
- Any proposed policy that modifies wildcard permissions, grants critical admin capabilities, or affects more than 2 distinct system roles is marked `requiresConfirmation: true`.
- Generates a content-bound HMAC confirmation token based on the deterministic JSON hash of the diff payload and proposed version.
- Policy commits attempting broad changes without supplying the valid confirmation token are rejected with HTTP 409 `confirmation_required` / `PermissionConfirmationRequiredError`.

## Operational Paths

### Normal Path
1. Maintainer submits candidate policy payload to `POST /admin/permissions/preview`.
2. System evaluates diff against active policy (`version: N`).
3. If narrow and non-breaking, returns `preview` with `requiresConfirmation: false` and summary statistics.
4. Maintainer invokes `POST /admin/permissions/prepare` to generate the next staged version candidate (`version: N+1`).

### Failure Path
- **Invalid Policy**: Missing required fields, unknown permission names, or malformed role maps trigger HTTP 400 `InvalidPolicyError`.
- **Stale Base Policy**: If another administrator committed changes concurrently (`baseVersion !== current.version`), rejected with HTTP 409 `stale_policy` / `StalePolicyInputError`.
- **Unconfirmed Broad Change**: Attempting to commit broad modifications without matching confirmation token fails with HTTP 409 `confirmation_required`.

### Retry & Concurrency Path
- Stale version conflicts return HTTP 409 with current version metadata.
- Clients retry by fetching the latest policy version via `GET /admin/permissions/current` (or re-running preview with updated `baseVersion`), reviewing updated diffs, and re-signing the generated confirmation token.

### Authorization Path
- All preview, report, and prepare endpoints are guarded by `guard` and strictly require `req.principal.role === "maintainer"`.
- Requests from unauthorized roles (`user`, `service`) or unauthenticated callers fail immediately with HTTP 403 `maintainer role required` or HTTP 401 unauthorized.

## Edge Cases, Recovery, and Rollback

### Edge Cases
1. **Empty Actor Inventory**: When no explicit actors are mapped to roles, actor diffs gracefully resolve to empty arrays while role diffs compute normally.
2. **Permission Order Invariance**: Permission arrays are sorted and deduplicated prior to diffing, ensuring identical sets in different array order produce `isNoOp: true`.
3. **Redundant Permission Grants**: Adding a permission already present on a role produces no diff item and does not trigger confirmation.

### Rollback & Recovery
- All staged changes generated by `prepare` are non-activating candidates. Active policy remains unaltered until an explicit migration transaction executes.
- To rollback an applied policy change, maintainers can apply a previous version's configuration using the same preview pipeline, generating a reverse diff and confirmation token.
