# Recovery-path fixture generators

Issue #998. `lib/recovery-fixture-generator.ts` *generates* a deterministic
corpus of fixtures for the rare failure and recovery paths that are painful to
reproduce by hand: a sequence-number clash that must be re-sequenced, a fee
surge, a permanent auth failure, and a submission that times out and later turns
out to have been applied on-chain.

The generated corpus is committed at
[`tests/fixtures/recovery-paths/corpus.json`](../tests/fixtures/recovery-paths/corpus.json)
and is regenerated by a CLI (`pnpm fixtures:recovery`). Because the generator is
deterministic, the committed file is a golden artifact a reviewer can diff.

## Accuracy: real Stellar result codes

Failure codes are the actual Stellar/Horizon transaction result codes, with the
exact `tx_*` snake_case strings Horizon returns, and each code's `retryable`
flag and recovery action follow the Horizon result-code reference:

| Result code | Layer | Retryable | Recovery action | Why |
|---|---|---|---|---|
| `tx_success` | on-chain | — | none | applied |
| `tx_bad_seq` | on-chain | yes | resequence | valid only with a corrected sequence number |
| `tx_insufficient_fee` | on-chain | yes | bump_fee | fee too small for the surge |
| `tx_too_late` | on-chain | yes* | rebuild_time_bounds | ledger close time passed maxTime; envelope expired |
| `tx_bad_auth` | on-chain | **no**† | abort | wrong network passphrase (unsignable as-is) |
| `tx_failed` | on-chain | **no**† | abort | an operation failed; nothing applied |
| `rpc_unavailable` | transport | yes | resend | no on-chain result; same envelope safe to resend |
| `submission_timeout` | transport | yes | recheck_by_hash | confirm by hash before resend (avoid double-apply) |
| `app_forbidden` | application | **no** | abort | rejected by authorization before any tx was built |

\* `tx_too_late` is retryable only by rebuilding the envelope with new time
bounds; the signed envelope itself is dead. † Horizon documents `tx_bad_auth`
and `tx_failed` as *conditionally* recoverable (a missing-signature `tx_bad_auth`
can be re-signed; a `tx_failed` depends on the failed operation). The fixtures
model the **permanent** sub-case, which is the conservative default — recovery
code must never blind-retry an auth or operation failure. `RESULT_SEMANTICS` in the module is
the single source of truth for this table — every generated attempt reads its
`retryable`/`recoveryAction` from it, so a fixture can never claim a policy the
protocol contradicts. The two transport codes and `app_forbidden` are the paths
that never reach consensus, named without the `tx_` prefix to keep the layer
explicit. These match the codes the repo's own sandbox already emits
(`backend/src/sandbox/escrowAdapters.ts` returns `resultCode: "tx_bad_seq" |
"tx_bad_auth" | "tx_success"`, exercised by `backend/src/sandbox/fixtures.ts`).

Sources: Horizon [transaction result codes](https://developers.stellar.org/docs/data/apis/horizon/api-reference/errors/result-codes/transactions).

## Paths covered

The canonical corpus (`canonicalRecoveryCorpus`) has one representative fixture
per rare path/result code; the generator guarantees they are always present and
internally consistent:

| Path | Fixture | Shape | Terminal | Rollback |
|---|---|---|---|---|
| `normal` | `normal-single-success` | `tx_success` | `succeeded` | no |
| `retry` | `retry-bad-seq-resequenced` | `tx_bad_seq` → resequence → `tx_success` | `succeeded` | no |
| `retry` | `retry-fee-surge-bumped` | `tx_insufficient_fee` → bump fee → `tx_success` | `succeeded` | no |
| `retry` | `retry-rpc-transient-resend` | 2× `rpc_unavailable` → resend → `tx_success` | `succeeded` | no |
| `retry` | `retry-exhausted-rollback` | 3× `tx_bad_seq`, budget exhausted | `failed` | **yes** |
| `failure` | `failure-too-late-expired` | `tx_too_late`, intent abandoned | `failed` | no |
| `failure` | `failure-bad-auth-permanent` | `tx_bad_auth` (wrong network) | `failed` | no |
| `failure` | `failure-op-revert` | `tx_failed` | `failed` | no |
| `authorization` | `authorization-forbidden-actor` | `app_forbidden`, pre-submission | `failed` | no |
| `recovery` | `recovery-timeout-divergence-compensated` | `submission_timeout`, then found applied on-chain | `compensated` | **yes** |

`generateRecoveryCorpus({ retryVariants })` appends additional deterministic
retry variants (the committed corpus uses 8), each with a seed-chosen retryable
code and failure count before success.

## Fixture contract

`RecoveryFixture` (see the module for the full type). Key invariants, all
enforced by `validateRecoveryFixture` and asserted in tests:

- `attempts` are 1-based and contiguous, and `attempts.length <= maxAttempts`.
- Each attempt's `resultCode` is a known code, and its `retryable` /
  `recoveryAction` **must equal** the `RESULT_SEMANTICS` entry for that code —
  the validator rejects a tampered policy.
- `recovery.compensations` is non-empty **iff** `recovery.rollbackRequired` is
  true. This is the central recovery/rollback invariant: a rollback always has
  explicit, ordered compensation steps, and steps never exist without a rollback.

`validateRecoveryFixture` is the same guard shape as `validateRepairScenario`
(`backend/src/services/repairScenarioFixtures.ts`), so a consumer can safely load
a hand-edited corpus and reject a malformed one.

## Operational edge cases & rollback

| Case | Modelled by | Expected recovery |
|---|---|---|
| Sequence clash | `tx_bad_seq` | rebuild with a fresh sequence number, then resubmit |
| Fee surge | `tx_insufficient_fee` | resubmit with a higher fee / fee-bump |
| Envelope expired | `tx_too_late` | rebuild with new time bounds (old envelope is dead) |
| Transport failure | `rpc_unavailable` | resend the same signed envelope (no on-chain result) |
| No confirmation | `submission_timeout` | **recheck by hash** before resending to avoid double-apply |
| Retry budget exhausted | 3× failing code at `maxAttempts` | mark failed, run compensations, release reserved resources |
| Wrong network / op revert | `tx_bad_auth` / `tx_failed` | permanent: fail fast, no compensation (nothing applied) |
| Unauthorized actor | `app_forbidden` | reject before any transaction is built; terminal |
| Submitted-then-diverged | `submission_timeout` + on-chain success | **compensate**: reconcile local state to the applied result |

The `compensated` terminal state is distinct from `failed`: `failed` means
nothing was applied, while `compensated` means a side effect existed (or the
transaction was applied on-chain despite a local timeout) and local state was
reconciled to match reality. The `submission_timeout` → `recheck_by_hash` rule
is the key safety property — a naive resend after a timeout risks a double-apply.

## Regenerating and the drift guard

```bash
pnpm fixtures:recovery           # regenerate the committed corpus.json
pnpm fixtures:recovery --check   # fail (non-zero) if the committed corpus is stale
```

`--check` regenerates in-memory and diffs against the committed file. Run it in
CI next to the other fixture/drift checks (`check:drift`, `fixtures:regenerate`)
so the generator and its committed output can never diverge. The seed and
variant count are recorded in the file header so a change to them is reviewable.

## Complexity

`generateRecoveryFixture` is O(k) in the attempt count; `canonicalRecoveryCorpus`
is O(F·k̄) for `F` fixtures of mean length `k̄`; `generateRecoveryCorpus` adds
O(v·k̄) for `v` variants; `validateRecoveryFixture` is O(k); `makeRng` is O(1)
per draw. No clock or global RNG is read, so output is byte-identical across runs.

## Preserving existing contracts

Purely additive: a new `lib/` module, its test, a committed JSON artifact, a CLI,
and one `package.json` script. Nothing existing is modified or removed, and the
generator reuses the Stellar result-code vocabulary the sandbox already emits
rather than introducing a parallel one — so there is no migration to perform.

## Tests

`lib/recovery-fixture-generator.test.ts` (run with `pnpm test`) asserts full path
and result-code coverage, the Stellar semantics mapping, the recovery/rollback
invariants, determinism (byte-stable corpus, seed-sensitive variants), and the
validator's rejection cases (including tampered policy fields).
